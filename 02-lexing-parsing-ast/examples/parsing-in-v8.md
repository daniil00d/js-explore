# Разбор внутри V8: preparser, ленивость и кеши

Всё, что в этом разделе делалось с acorn и Babel, движок делает тоже — только
с другими целями. Инструменту дерево нужно как результат, движку — как промежуточный
материал: сразу после генерации байткода дерево выбрасывается. Отсюда все решения
V8 про разбор: чем меньше и позже, тем лучше.

Числа ниже получены на `node v22.14.0 / V8 12.4` и воспроизводятся
[`lazy-parsing.mjs`](./lazy-parsing.mjs).

## Конвейер

```
байты файла
  → декодирование (UTF-8 → UTF-16)
  → сканер: поток токенов
  → preparser (для функций) либо parser (для того, что нужно сейчас)
  → AST
  → генератор байткода Ignition
  → AST выбрасывается
```

Два наблюдения из этой схемы. Первое: дерево живёт считанные микросекунды и наружу
не отдаётся — никакого «AST V8», с которым можно поработать, не существует. Второе:
до байткода добирается не весь файл, а только то, что действительно понадобилось.

## Сканер

Сканер работает с UTF-16 и по одному-двум символам за раз, поэтому его стоимость
линейна по размеру файла — со всем файлом, а не с исполняемой частью. В
[статье про сканер](https://v8.dev/blog/scanner) команда V8 описывает, сколько сил
ушло на оптимизацию именно этого места: до трети времени компиляции скрипта уходило
на декодирование и склейку строк.

Практическое следствие: способ доставки влияет на старт. Для однобайтового текста
у V8 отдельный, более быстрый путь, а неиспользуемый код всё равно сканируется
целиком — просто потому, что лежит в том же файле.

## Preparser: разбор ради того, чтобы не разбирать

Функцию, которую сейчас никто не вызывает, V8 не разбирает полностью. Вместо этого
работает preparser: он проходит по телу, проверяет синтаксис и выясняет, какие
переменные функция захватывает из внешних областей. Дерево не строится, байткод
не генерируется.

В логе `--log-function-events` это видно так:

| Событие | Что произошло |
| --- | --- |
| `preparse-no-resolution` | предразбор без разрешения имён |
| `preparse-resolution` | предразбор с разрешением имён |
| `full-parse` | полный разбор с построением дерева |
| `parse-function` | полный разбор функции при первом вызове |
| `parse` | разбор стрелочной функции |
| `interpreter` | сгенерирован байткод |
| `first-execution` | первый вызов |

Вызванная функция получает предразбор при компиляции скрипта, а потом полный разбор
при первом вызове: её тело читается дважды. Это осознанная сделка. Статистика
говорит, что большая часть кода на странице не выполняется никогда, поэтому дешевле
переплатить на редких повторных разборах, чем разбирать всё сразу.

Замер на файле из 3000 функций (642 КиБ), только компиляция, без выполнения:

| Режим | Время |
| --- | --- |
| по умолчанию (ленивый разбор) | ~6 мс |
| `--no-lazy` (полный разбор всего) | ~19 мс |

Разница примерно в три раза — и это верхняя оценка выигрыша ленивости.

## Подсказка немедленной компиляции: трюк со скобками

Если функция вызывается сразу, предразбор — чистая потеря. V8 угадывает это по
символу перед словом `function`: скобка и `!` включают немедленный полный разбор,
а `void` — нет.

| Код | Первое событие |
| --- | --- |
| `(function f() {...})(1)` | `full-parse` |
| `!function f() {...}(1)` | `full-parse` |
| `void function f() {...}(1)` | `preparse-resolution`, затем `full-parse` |

Что это именно подсказка, а не что-то более глубокое, проверяется флагом
`--max-lazy` («ignore eager compilation hints»): под ним разница между обёртками
исчезает и все функции начинают с предразбора.

Историческое следствие — инструмент [optimize-js](https://github.com/nolanlawson/optimize-js),
который расставлял такие скобки при сборке. Сегодня он не нужен: код на реальных
страницах приходит с кешем, а сам V8 стал считать иначе. Знать про эвристику
всё равно полезно — она объясняет, почему два одинаковых по смыслу бандла могут
стартовать по-разному.

## Стрелочные функции и cover grammar

В логе стрелочные функции отмечаются отдельным событием `parse`, а не так, как
обычные. Причина — в грамматике: `(a, b)` может оказаться и выражением с запятой,
и списком параметров, и понять это можно только дойдя до `=>`. Спецификация решает
задачу через cover grammar, а реализация платит за это перечитыванием участка.

То же самое в примере [`precedence.mjs`](./precedence.mjs) видно с другой стороны:
`(a, b)` и `(a, b) => a` дают совершенно разные деревья при одинаковом начале.

## Кеши: три разных механизма

**Кеш компиляции внутри процесса.** Один и тот же исходник с тем же именем файла
компилируется повторно почти бесплатно. Отключается флагом `--no-compilation-cache`,
и без этого флага любые замеры разбора врут: вторая попытка покажет нули.

**Code cache между запусками.** Байткод можно сериализовать и потом загрузить
вместо разбора. В браузере это происходит само, в Node доступно через API:

```js
import vm from 'node:vm';
const script = new vm.Script(source, { filename: 'g.js' });
const cachedData = script.createCachedData();       // сохранить рядом с файлом
const fast = new vm.Script(source, { filename: 'g.js', cachedData });
console.log(fast.cachedDataRejected);               // false, если кеш подошёл
```

На том же файле из 3000 функций (642 КиБ): разбор с нуля ~8 мс, компиляция
с готовым кешем ~0.9 мс, размер кеша ~246 КиБ. То есть кеш весит около трети
исходника и экономит почти всё время компиляции. Привязан он к версии V8 и набору
флагов: при несовпадении `cachedDataRejected` станет `true`, и V8 молча разберёт
файл заново.

**Снимки (snapshots).** Встроенные объекты и код самого движка не разбираются при
каждом старте, а поднимаются из готового образа памяти. Node пользуется этим же
механизмом для своей внутренней библиотеки, а с недавних версий — и для
пользовательского кода через `--build-snapshot`. Подробности — в разделе 08.

Отдельно стоит streaming compilation: браузер начинает разбор скрипта, ещё не
докачав его до конца, на фоновом потоке. В Node этого нет, но флаг
`--no-lazy-streaming` в списке остался.

## Что с этим делать на практике

- **Размер стартового чанка важнее общего размера бандла.** Всё, что попало
  в стартовый файл, будет просканировано, а всё, что вызывается на старте, —
  разобрано и превращено в байткод. Код, вынесенный в ленивый чанк, не стоит ничего,
  пока не понадобится.
- **Мёртвый код стоит денег даже без выполнения.** Не срабатывающий tree shaking
  бьёт не только по трафику: непользуемые функции всё равно проходят сканер
  и preparser.
- **Замеры разбора надо изолировать.** `new vm.Script(source)` с
  `--no-compilation-cache` — минимальный честный замер. Всё остальное
  (`node file.js` с секундомером) меряет заодно старт процесса и выполнение.
- **Ленивость можно выключить и посмотреть.** `--no-lazy` даёт верхнюю границу
  стоимости разбора, `--max-lazy` — нижнюю. Разница между ними и есть тот запас,
  которым распоряжается движок.
