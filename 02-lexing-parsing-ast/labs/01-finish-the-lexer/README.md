# Лаба 02-1. Допиши лексер

**Сложность:** средняя. **Что тренируем:** лексический разбор и его границы.

## Задача

В [`tokens.mjs`](./tokens.mjs) лежит лексер из примеров раздела, из которого убраны
три куска. Нужно их вернуть:

1. **Числа.** Все формы: `0x1f`, `0b1010`, `0o17`, `1_000`, `.5`, `1e-3`, `1.5e+10`, `10n`.
2. **Приватные имена.** `#value` — один токен типа `private`, а не `#` плюс имя.
3. **Регулярка или деление.** Главное решение любого JS-лексера.

Третий пункт — основной. Начать можно с простого правила «после значения деление,
после оператора регулярка», но на тестах вылезет случай, который так не решается:

```js
const mid = (a + b) / 2;      // деление
if (ready) /^\d+$/.test(s);   // регулярка
```

Предыдущий токен в обоих случаях — `)`. Значит, одного предыдущего токена мало,
и лексеру придётся помнить, что за скобку он закрыл.

Шаблонные строки в лабе не проверяются: они берутся одним куском, и почему их
нельзя разобрать без парсера, показано в [`../../examples/tokenize.mjs`](../../examples/tokenize.mjs).

## Как проверить

```bash
node 02-lexing-parsing-ast/labs/01-finish-the-lexer/check.mjs
```

Эталон — настоящий лексер `acorn`. Проверка прогоняет девятнадцать фрагментов
через оба лексера и сравнивает потоки токенов целиком: тип, текст и флаг
`newlineBefore` (тот, из которого потом получается ASI).

С заготовкой проходят три проверки из девятнадцати. Это нормально: часть
фрагментов не содержит ни чисел, ни `#`, ни двусмысленного слеша.

## С чего начать

Посмотреть, как выглядит правильный ответ для одного фрагмента:

```bash
node -e "
const acorn = require('acorn');
const src = 'if (ready) /^\\\\d+\$/.test(input);';
for (const t of acorn.tokenizer(src, { ecmaVersion: 'latest' })) {
  console.log(t.type.label.padEnd(10), JSON.stringify(src.slice(t.start, t.end)));
}
"
```

И запустить пример раздела, где та же неоднозначность разобрана на пальцах:

```bash
node 02-lexing-parsing-ast/examples/tokenize.mjs
```

## Если застрял

<details>
<summary>Числа: три места, где легко ошибиться</summary>

- знак после экспоненты: в `1e-3` минус входит в число, в `1-3` нет;
- в `1..toString()` первая точка принадлежит числу (`1.`), вторая уже нет;
- в `0x1f.toString()` точка числу не принадлежит вообще — у шестнадцатеричного
  литерала дробной части не бывает.

Проще разобрать отдельно два случая: с префиксом системы счисления и без него.
</details>

<details>
<summary>Регулярка: с чего начать правило</summary>

Регулярка допустима там, где ожидается значение. Значит, `/` — это деление, если
предыдущий токен был значением: число, строка, регулярка, имя, `]`, `++`, `--`,
а также `this`, `super`, `null`, `true`, `false`. После всего остального —
регулярка.
</details>

<details>
<summary>Скобка: как всё-таки различить два случая</summary>

Завести стек. На каждом `(` кладём в него признак «перед скобкой стояло
`if`/`while`/`for`/`with`», на каждом `)` снимаем и записываем в токен, например
в поле `afterControlHead`. Тогда `regexAllowedAfter` смотрит не только на тип
предыдущего токена, но и на это поле.
</details>

<details>
<summary>А что с закрывающей фигурной скобкой?</summary>

Там та же неоднозначность, но неразрешимая на уровне лексера:

```js
{}            /re/.test(s)   // блок, дальше регулярка
const o = {}; o /  2         // объектный литерал, дальше деление
```

Чтобы решить это правильно, нужно знать, было ли `{` началом блока или литерала,
а это уже работа парсера. Настоящие лексеры (в том числе acorn) получают эту
подсказку от парсера — поэтому «независимый лексер» в JavaScript и не существует.
В проверке таких фрагментов нет.
</details>
