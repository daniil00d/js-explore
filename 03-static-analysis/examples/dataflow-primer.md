# Анализ потока данных: устройство и словарь

Все анализы из этого раздела — один и тот же алгоритм с разными параметрами.
Стоит увидеть схему один раз, и дальше новый анализ читается как заполнение
четырёх полей в анкете. Живые реализации — в [`dataflow.mjs`](./dataflow.mjs)
и [`constant-folding.mjs`](./constant-folding.mjs).

## Схема: четыре вопроса

Любой анализ потока данных задаётся ответами на четыре вопроса.

| Вопрос | Варианты | Пример |
| --- | --- | --- |
| **Направление** | вперёд или назад | достигающие определения — вперёд, живость — назад |
| **Что распространяем** | множество фактов или элемент решётки | множество определений; описание значения |
| **Как сливаем на развилке** | объединение или пересечение | «может быть» — объединение, «обязательно» — пересечение |
| **Как факт меняется на инструкции** | функция передачи | `OUT = (IN \ KILL) ∪ GEN` |

Дальше механика одинаковая: расставить начальные значения, пересчитывать блоки,
пока хоть что-то меняется. Такой цикл называется вычислением неподвижной точки
(fixpoint), а порядок обхода влияет только на скорость, не на результат.

```
пока что-то менялось:
  для каждого блока B:
    IN[B]  = слить(OUT[P] для всех предшественников P)
    OUT[B] = передать(IN[B], инструкции B)
```

Для анализа назад всё зеркально: `OUT` собирается из последователей, `IN`
считается по инструкциям в обратном порядке.

## Классические анализы

| Анализ | Направление | Слияние | Отвечает на вопрос | Кому нужен |
| --- | --- | --- | --- | --- |
| Reaching definitions | вперёд | объединение | какие записи могли дать это значение | предупреждение «читается до присваивания» |
| Liveness | назад | объединение | понадобится ли ещё значение переменной | распределение регистров, мёртвые записи |
| Available expressions | вперёд | пересечение | вычислено ли уже это выражение | вынос общих подвыражений (CSE) |
| Very busy expressions | назад | пересечение | будет ли выражение вычислено на всех путях | подъём вычислений |
| Constant propagation | вперёд | решётка | известно ли значение точно | свёртка, отсечение ветвей |
| Definite assignment | вперёд | пересечение | присвоено ли на всех путях | «переменная используется до присваивания» в TS |
| Taint analysis | вперёд | объединение | могло ли значение прийти от пользователя | поиск уязвимостей, CodeQL и Semgrep |

Два столбца здесь важнее остальных. **Направление** определяет, на какой вопрос
анализ вообще способен ответить: «откуда пришло» — только вперёд, «понадобится
ли» — только назад. **Слияние** определяет силу утверждения: объединение даёт
«может быть» (may), пересечение — «обязательно» (must).

## Почему это останавливается

Ключевое свойство — не сложность, а монотонность.

1. Значения берутся из решётки конечной высоты. У констант это три уровня:
   `⊥` → конкретное значение → `⊤`. У множеств определений высота равна числу
   определений.
2. Функция передачи монотонна: если знание на входе стало менее точным, на
   выходе оно точнее не станет.
3. Значения меняются только в одну сторону — теряют точность.

Из трёх пунктов следует, что число изменений конечно, а значит, цикл завершится.
Это не эвристика, а теорема о неподвижной точке, и именно она отвечает на вопрос
«почему анализ цикла не крутится вечно, если сам цикл может».

Обратная сторона: анализ обязан **терять** точность, иначе он не остановится.
Когда на слиянии путей встречаются `label = "а"` и `label = "б"`, единственный
корректный ответ — `⊤`, «что-то из двух, не знаю что».

## Приёмы, повышающие точность

| Приём | Что даёт | Чем платим |
| --- | --- | --- |
| SSA-форма | цепочки use-def бесплатно, φ вместо анализа слияний | нужен пересчёт при каждом изменении графа |
| Отсечение невыполнимых рёбер (SCCP) | ветвь под ложным условием не портит результат | анализ и достижимость считаются вместе |
| Расширение решётки (интервалы, множества значений) | `x ∈ [0, 10]` вместо `⊤` | шире решётка — дольше сходимость, нужен widening |
| Чувствительность к контексту вызова | разные ответы для разных вызывающих | экспоненциальный рост числа контекстов |
| Чувствительность к путям | учёт условий вида «здесь x > 0» | число путей растёт экспоненциально |

Первые два приёма почти бесплатны, поэтому применяются везде. Последние два —
причина, по которой академические анализаторы точнее промышленных, но работают
на программах в тысячу строк, а не в миллион.

## Виды чувствительности

Термины, которые встречаются в любой статье по теме.

- **Flow-insensitive** — порядок инструкций игнорируется, у переменной одно
  описание на всю функцию. Самый грубый и самый быстрый вариант; так работает
  вывод «эта переменная где-то перезаписывается».
- **Flow-sensitive** — учитывается порядок и точка программы. Всё в этом
  разделе — flow-sensitive.
- **Path-sensitive** — учитываются условия на пути: после `if (x !== null)` в
  ветви `x` не null. Это ровно то, что TypeScript называет сужением типов
  (narrowing), и что разбирается в разделе 05.
- **Context-sensitive** — функция анализируется отдельно для каждого места
  вызова. Без этого `identity(1)` и `identity("а")` сливаются в `⊤`.
- **Field-sensitive** — различаются поля объекта: `obj.a` и `obj.b` — разные
  ячейки. В JavaScript упирается в `obj[key]`.

## Как это выглядит в реальных инструментах

| Инструмент | Где здесь анализ потока данных |
| --- | --- |
| ESLint | `CodePathAnalysis` — свой граф путей; на нём стоят `no-unreachable`, `consistent-return`, `no-fallthrough` |
| TypeScript | control flow analysis для сужения типов и `strictNullChecks`; path-sensitive по конструкции |
| Terser, esbuild | свёртка констант, устранение мёртвого кода, слияние переменных |
| Closure Compiler | самый полный набор: type inference, escape-анализ, межпроцедурные оптимизации |
| CodeQL, Semgrep | taint-анализ: путь от источника недоверенных данных до опасного вызова |
| V8 (TurboFan) | SSA, свёртка, вынос инвариантов, устранение проверок — но с опорой на данные рантайма |

Последняя строка — самая интересная. У движка есть то, чего нет ни у одного
статического анализатора: наблюдения за настоящими запусками. Поэтому V8 может
не доказывать, а предполагать — и проверять предположение. Как именно, — разделы
[10](../../10-inline-caches-and-shapes) и [11](../../11-optimization-and-deopt).

## Что читать

- [Static Program Analysis](https://cs.au.dk/~amoeller/spa/) — Møller и
  Schwartzbach, бесплатная книга. Первые пять глав покрывают всё, что здесь
  написано, но с доказательствами.
- [Principles of Program Analysis](https://link.springer.com/book/10.1007/978-3-662-03811-6) —
  Nielson, Nielson, Hankin. Классика, тяжёлая, но исчерпывающая.
- [Cytron et al., Efficiently computing static single assignment form](https://dl.acm.org/doi/10.1145/115372.115320) —
  оригинальная статья про размещение φ через фронты доминирования; алгоритм из
  [`ssa.mjs`](./ssa.mjs) взят оттуда.
- [Wegman & Zadeck, Constant propagation with conditional branches](https://dl.acm.org/doi/10.1145/103135.103136) —
  тот самый SCCP.
- [ESLint code path analysis](https://eslint.org/docs/latest/extend/code-path-analysis) —
  документация к графу путей, на котором пишутся правила.
