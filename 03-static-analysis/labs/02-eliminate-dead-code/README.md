# Лаба 03-2. Выброси мёртвый код

**Сложность:** средняя. **Что тренируем:** достижимость на графе потока управления.

## Задача

Реализовать в [`eliminate.mjs`](./eliminate.mjs) функцию `eliminate(source)`: найти
инструкции, до которых управление не доходит ни при каких данных, и убрать их из текста.

```js
eliminate(source);
// → { code: '...', removed: [7, 15] }
```

`removed` — номера строк исходного файла, от единицы, по возрастанию, без повторов.
`code` — тот же файл минус эти строки: удалённая строка исчезает целиком, остальные
остаются байт в байт. Это удаление, а не переформатирование.

Граф строить не нужно, он готовый — тот же, что в примерах раздела:

```js
import { buildCfg, reachableBlocks } from '../../examples/cfg.mjs';
```

## Почему это нельзя сделать по дереву

Половину случаев на дереве действительно видно: инструкция стоит после `return` в том же
блоке. На остальных форма кода не отличается от нормальной:

- `while (true)` без `break` — код после цикла недостижим, хотя написан сразу за ним;
- `continue` в середине тела — недостижим остаток тела, а не остаток функции;
- `break` после `return` внутри `case` — недостижима одна строка внутри `switch`;
- `if (false) { ... }` — недостижимо тело, при том что строка с условием выполняется.

Всё это — вопрос «есть ли путь от входа до блока», то есть вопрос к графу. Ответ даёт
`reachableBlocks(cfg)`: всё, чего в нём нет, недостижимо.

## Две вещи, на которых легко ошибиться

**Граф строится на функцию, а не на модуль.** Для внешней функции вложенная — это одна
инструкция; её внутренний поток управления снаружи не виден. Значит, графов нужно
столько, сколько в файле функций, включая стрелки и колбэки.

**Объявления не удаляются.** `function helper()` после `return` недостижим как
инструкция, но привязка `helper` создаётся при входе в функцию — и вызов выше работает.
То же с `var`. Недостижимость инструкции и бесполезность объявления — разные
утверждения; в [`fixtures/after-return.mjs`](./fixtures/after-return.mjs) на этом стоит
живой код.

## Как проверить

```bash
node 03-static-analysis/labs/02-eliminate-dead-code/check.mjs
```

Ожидаемые строки взяты не из файла с ответами, а из самих фикстур: то, что должно быть
удалено, помечено в них комментарием `// мёртвый`. Кроме этого проверяются три свойства:

- **поведение сохранилось** — фикстура выполняется до и после правки, результат `main()`
  сравнивается. Здесь ловится удаление всплывающего объявления;
- **остальное цело** — результат обязан совпасть с «файл минус удалённые строки»;
- **движок подтверждает** — фикстура запускается с `NODE_V8_COVERAGE`, и проверяется, что
  ни одна из удалённых строк при запуске не выполнялась.

Последняя проверка работает только в одну сторону, и это принципиально. Недостижимый код
выполниться не может, поэтому «удалили строку, которая выполнялась» — точно ошибка
анализа. Обратное неверно: в фикстурах полно живых строк, которые в этом запуске не
выполнились. Покрытие говорит «не выполнялось на этих данных», анализ — «не выполнится ни
при каких». Первое зависит от тестов, второе нет.

## С чего начать

```bash
node 03-static-analysis/examples/build-cfg.mjs
```

Пример печатает граф целиком, с рёбрами и пометкой недостижимых блоков, — по нему видно,
как выглядит то, что нужно найти. Дальше:

```js
const cfg = buildCfg(functionNode, source);
const reachable = reachableBlocks(cfg);
for (const block of cfg.blocks) {
  if (reachable.has(block)) continue;
  for (const statement of block.statements) {
    // statement.node, statement.line, statement.start, statement.end
  }
}
```

## Если застрял

<details>
<summary>Как собрать все функции файла</summary>

```js
const functions = [];
const collect = (node) => functions.push(node);
walk.simple(ast, {
  FunctionDeclaration: collect,
  FunctionExpression: collect,
  ArrowFunctionExpression: collect,
});
```

Метод объекта и метод класса — это `FunctionExpression`, отдельного типа для них нет.
</details>

<details>
<summary>Инструкция занимает несколько строк</summary>

У узла есть `loc.start.line` и `loc.end.line` — удалять нужно весь диапазон. Номера
удобно копить в `Set`: одна и та же строка легко приходит дважды, а в ответе она должна
быть один раз и список должен быть отсортирован по возрастанию.
</details>

<details>
<summary>Почему break после return вообще попадает в граф</summary>

`break` — это инструкция, и `buildCfg` создаёт для неё блок. Но предшественников у этого
блока нет: предыдущая инструкция была `return`, и ребро оттуда ведёт в выход функции.
Блок без пути от входа — ровно то, что ищет `reachableBlocks`.
</details>

## Критерий готовности

`16 из 16`.

## Что здесь упрощено

Мы удаляем инструкции графа, а настоящий оптимизатор удаляет поддеревья. Разница видна
на `if (false) { ... }`: тело мы убираем, а сам `if` остаётся, потому что строка с
условием достижима. Terser в этом месте выбросит весь `if`, но для этого ему нужно не
только знать, что тела не достичь, а ещё и уметь вычислить условие — это следующая лаба.
Из тех же соображений в фикстурах нет вложенных `if` внутри недостижимых участков:
удаление по строкам оставило бы от них висящую закрывающую скобку.

## Куда это ведёт дальше

Достижимость — первый анализ, который считают на графе, и самый дешёвый. На том же графе
дальше считаются живость переменных и достигающие определения
([`dataflow.mjs`](../../examples/dataflow.mjs)), доминаторы и SSA
([`ssa.mjs`](../../examples/ssa.mjs)). В инструментах это правило `no-unreachable` в
ESLint ([раздел 04](../../../04-linters-and-codemods)), dead code elimination в
минификаторах и tree shaking в сборщиках ([раздел 07](../../../07-bundlers)), а внутри
V8 — отказ генерировать байткод для блоков, до которых нет пути
([раздел 09](../../../09-bytecode)).
