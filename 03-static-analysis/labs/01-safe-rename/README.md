# Лаба 03-1. Безопасное переименование

**Сложность:** средняя. **Что тренируем:** чтение дерева областей видимости и выводы из него.

## Задача

Реализовать в [`rename.mjs`](./rename.mjs) функцию `rename(source, request)`, которая
переименовывает одну переменную — или отказывается, если переименование меняет смысл
программы:

```js
rename(source, { name: 'total', line: 5, to: 'sum' });
// → { ok: true, code: '...' }
// → { ok: false, reason: '«sum» уже объявлен в этой же области (стр. 6)' }
```

Переменная задаётся именем **и строкой объявления**: одно и то же имя в файле может быть
объявлено много раз, а переименовать нужно ровно одно из объявлений — вместе со всеми
ссылками именно на него.

Сам scope-анализ писать не нужно: берём готовый из примеров раздела.

```js
import { allBindings, analyzeScopes } from '../../examples/scope.mjs';
```

Интересное в лабе начинается после него. Анализ отвечает на вопрос «какая ссылка куда
ведёт», а решение о том, можно ли трогать имя, приходится выводить самому.

## Когда переименовывать нельзя

Отказ — полноценный ответ, и это половина задания. Четыре причины, по одной на фикстуру:

| Причина | Что случится, если всё-таки переименовать |
| --- | --- |
| Имя занято в той же области | Два объявления одного имени рядом: `let sum` и `const sum` — это уже `SyntaxError` |
| Новое имя используется внутри области и приходит извне | Новое объявление встанет между ссылкой и её объявлением: ссылка начнёт читать нашу переменную |
| Ссылка на нашу переменную стоит внутри области, где новое имя уже объявлено | Ссылка попадёт в чужое объявление, а не в наше |
| Внутри области есть прямой `eval` | Он видит область целиком и может обратиться к имени строкой, которой в тексте нет |

Первые три — это одна и та же проблема с трёх сторон: после правки какая-то ссылка
разрешится не туда, куда разрешалась. Четвёртая — принципиальная: про `eval`
корректного ответа не существует, есть только отказ.

В причине отказа нужно назвать то, что мешает: конфликтующее имя или `eval`. Проверка
именно это и смотрит, а не формулировку целиком.

## Что легко сломать

Ссылки на переменную — не все вхождения её имени в текст. Две ловушки, обе есть в фикстурах:

- **Затенение.** В [`shadowing.mjs`](./fixtures/shadowing.mjs) модульный `cache`
  переименовывается, а параметр `cache` другой функции обязан остаться `cache`:
  это другая переменная, просто с тем же именем.
- **Сокращённая запись свойства.** В `{ total, average }` и в `const { count } = source`
  один и тот же кусок текста работает и именем поля, и переменной. Заменить его целиком —
  значит поменять форму объекта. Правильная правка раскрывает сокращение:
  `{ total: sum }`, `const { count: hits } = source`.

Вторая ловушка — причина, по которой проверка запускает модуль до и после правки.

## Как проверить

```bash
node 03-static-analysis/labs/01-safe-rename/check.mjs
```

Правильных ответов в проверке нет. Запрос на переименование берётся из шапки фикстуры,
а результат оценивается тремя свойствами, которые считаются на месте:

- **поведение не изменилось** — модуль выполняется до и после правки (прямо из памяти,
  через `data:`-URL), и результат `main()` сравнивается;
- **имена разрешаются так же** — по результату повторно строится дерево областей
  видимости, и сверяется, в какое объявление ведёт каждая ссылка. Это свойство сильнее
  первого: оно ловит вхождения, которые в этом запуске просто не выполнились;
- **правка минимальна** — строк столько же, и меняются только строки с новым именем.
  Файл, перегенерированный из AST, эту проверку не проходит.

## С чего начать

```bash
node 03-static-analysis/examples/scope-analysis.mjs
```

Там та же таблица привязок, из которой всё и берётся: у привязки есть `scope`, `kind`,
`node` (объявляющий идентификатор) и `references` — все ссылки на неё. У ссылки есть
`name`, `scope`, `resolved` и `line`. У области — `bindings`, `parent`, `children`
и `chain` (цепочка до корня).

Полезно посмотреть и на то, как то же самое делает настоящий инструмент: `Rename Symbol`
в редакторе, `no-shadow` в ESLint, переименование локальных переменных в минификаторе.

## Если застрял

<details>
<summary>Как проверить, что область лежит внутри другой</summary>

`scope.chain` — это список областей от текущей до корня. Значит, «область `inner`
находится внутри `outer`» — это `inner.chain.includes(outer)`. Через ту же проверку
удобно спрашивать «а эта ссылка внутри нашей области?».
</details>

<details>
<summary>Как отличить «имя приходит извне» от «имя объявлено внутри»</summary>

У ссылки есть `resolved` — привязка, в которую она ведёт. Если `resolved.scope` лежит
внутри нашей области, ссылке ничего не грозит: между ней и её объявлением наше новое
объявление не влезет. Если снаружи (или `resolved === null`, то есть имя вообще не из
этого модуля) — переименование её перехватит.
</details>

<details>
<summary>Как найти прямой eval</summary>

Прямой `eval` — это ссылка с именем `eval`, которая ни во что не разрешилась: в модуле
такого объявления нет, имя приходит из глобального объекта. Именно поэтому анализ его
и видит: `const alias = eval` или `obj.eval` — уже другие случаи, и с ними анализ
проигрывает молча.
</details>

<details>
<summary>Как найти сокращённые свойства</summary>

У узла `Property` есть флаг `shorthand`. Но `key` и `value` у него — разные узлы
с одинаковыми позициями, поэтому вхождение из `binding.references` сравнивать с ними
нужно по `start`, а не по ссылке на объект.

И отдельная засада: `walk.simple(ast, { Property })` находит сокращения только в
литералах объектов. Внутрь `Property` шаблонов acorn-walk не заходит — у `ObjectPattern`
он сразу спускается в `prop.value`. Поэтому `const { count } = obj` этим обработчиком
не поймать, и свойства шаблона приходится перебирать самому.
</details>

<details>
<summary>Как применять правки к тексту</summary>

Идти нужно с конца файла к началу: первая же замена сдвигает позиции всех следующих
узлов. Тот же приём, что в лабе про кодмод из
[раздела 02](../../../02-lexing-parsing-ast/labs/03-surgical-codemod).
</details>

## Критерий готовности

`20 из 20`.

## Куда это ведёт дальше

Переименование — самая честная проверка scope-анализа: ошибка хотя бы в одной ссылке
сразу меняет поведение программы. На этом же анализе стоят `no-unused-vars`,
`prefer-const` и `no-shadow` из [раздела 04](../../../04-linters-and-codemods), а ещё
минификаторы: сокращение имён до одной буквы — это то же переименование, выполненное
для всех переменных сразу и с теми же четырьмя проверками. Оттуда же и правило
«минификатор сдаётся на `eval`» — [раздел 07](../../../07-bundlers).
