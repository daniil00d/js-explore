# Как читать ECMA-262: разбор одного оператора по шагам

Спецификация выглядит неприступной, но устроена однообразно: несколько десятков
соглашений, которые повторяются на всех восьми сотнях страниц. Разберём их на
одном выражении — `left + right` — и по ходу проверим каждый шаг реальным кодом
из [`plus-operator.mjs`](./plus-operator.mjs).

Ссылки ведут на живой черновик [tc39.es/ecma262](https://tc39.es/ecma262/). Это
единственный источник, который стоит читать: pdf-снапшоты вроде «ES2015» устарели,
а MDN описывает поведение, а не алгоритмы.

## Три вида разделов

Каждая языковая конструкция описана тремя способами, и путать их не стоит.

**Syntax** — грамматика в БНФ-подобной записи
([5.1.1 Context-Free Grammars](https://tc39.es/ecma262/#sec-context-free-grammars)).
Грамматик в спецификации несколько:
[лексическая](https://tc39.es/ecma262/#sec-lexical-and-regexp-grammars) режет текст
на токены, [синтаксическая](https://tc39.es/ecma262/#sec-syntactic-grammar) собирает
из токенов дерево. Отсюда, например, следует, что `/` — не один токен: в разных
контекстах это либо деление, либо начало регулярного выражения, и лексер обязан
знать, чего ждёт парсер.

**Static Semantics** — правила, проверяемые без выполнения
([5.2.5](https://tc39.es/ecma262/#sec-static-semantic-rules)). Здесь живут
[Early Errors](https://tc39.es/ecma262/#sec-error-handling-and-language-extensions)
и вспомогательные функции над деревом разбора вроде `BoundNames` или
`LexicallyDeclaredNames`. Это буквально статический анализ, только записанный
человеческим языком.

**Runtime Semantics** — алгоритмы выполнения
([5.2.4](https://tc39.es/ecma262/#sec-runtime-semantics)). Нумерованные шаги вида
«Let x be …», «Return …», которые движок обязан воспроизвести наблюдаемо.

## Обозначения, без которых текст не читается

| Запись | Что значит |
| --- | --- |
| `? Foo(x)` | Вызвать `Foo`, и если вернулась abrupt completion — немедленно вернуть её наружу |
| `! Foo(x)` | То же, но с утверждением: ошибки здесь быть не может |
| `« a, b »` | Список (List) — служебный тип спецификации, не массив JS |
| `%Symbol.toPrimitive%` | Ссылка на встроенное значение, недоступная пользовательскому коду |
| `Assert: …` | Проверка инварианта; в реализации ей ничего не соответствует |

Знаки `?` и `!` — сокращения для разворачивания Completion Record
([5.2.4.3](https://tc39.es/ecma262/#sec-returnifabrupt-shorthands)). Почти каждый
шаг любого алгоритма возвращает не значение, а
[Completion Record](https://tc39.es/ecma262/#sec-completion-record-specification-type):
пару «как завершились» и «с каким значением». Тип завершения — `normal`, `throw`,
`return`, `break` или `continue`.

Это не бюрократия, а способ описать исключения и `break` одним механизмом.
Проверить можно прямо из консоли:

```js
(function () {
  try { return 1 } finally { return 2 }
})()
// → 2
```

Блок `try` вернул completion `{ тип: return, значение: 1 }`, а `finally` заменил её
на свою. Отсюда же берётся значение завершения инструкций, которое видно через
`eval`:

```js
eval('2; var x = 5;')            // → 2, объявление не имеет значения завершения
eval('if (true) { }')            // → undefined
eval('for (let i = 0; i < 3; i++) { i }')  // → 2, последнее непустое значение тела
```

## Разбор: что происходит при `left + right`

Начинать поиск нужно с самого оператора:
[13.8.1 The Addition Operator ( + )](https://tc39.es/ecma262/#sec-addition-operator-plus)
занимает четыре строки и сразу отправляет к
[13.15.4 EvaluateStringOrNumericBinaryExpression](https://tc39.es/ecma262/#sec-evaluatestringornumericbinaryexpression).
Шаги там такие:

1. `Let leftRef be ? Evaluation of leftOperand.`
2. `Let lval be ? GetValue(leftRef).`
3. `Let rightRef be ? Evaluation of rightOperand.`
4. `Let rval be ? GetValue(rightRef).`
5. `Return ? ApplyStringOrNumericBinaryOperator(lval, opText, rval).`

Первое наблюдение: операнды вычисляются строго слева направо, и оба — до того, как
оператор вообще начал работать. Второе: между «вычислить» и «получить значение»
есть разница. `Evaluation` даёт Reference Record — описание того, *откуда* берётся
значение, а `GetValue` его читает. Для `obj.prop` именно в `GetValue` и вызывается
геттер.

Дальше [13.15.3 ApplyStringOrNumericBinaryOperator](https://tc39.es/ecma262/#sec-applystringornumericbinaryoperator):

1. Если оператор — `+`:
   1. `Let leftPrimitive be ? ToPrimitive(leftValue).`
   2. `Let rightPrimitive be ? ToPrimitive(rightValue).`
   3. Если хотя бы один из них строка — привести оба к строкам и склеить.
   4. Иначе — переприсвоить `lval` и `rval` примитивами и идти дальше.
2. `Let lnum be ? ToNumeric(lval).`
3. `Let rnum be ? ToNumeric(rval).`
4. Если типы `lnum` и `rnum` не совпадают — `TypeError` (это про смешивание BigInt
   с Number).
5. Применить числовую операцию.

Второе наблюдение: приведение к примитивам тоже идёт слева направо, но уже *после*
того, как вычислены оба операнда. Значит, порядок побочных эффектов такой:
левый операнд, правый операнд, `ToPrimitive` левого, `ToPrimitive` правого. Ровно
это и печатает `plus-operator.mjs` в первом разделе вывода — четыре шага в
предсказанном порядке.

Обратите внимание, что `ToPrimitive` вызывается **без второго аргумента**: подсказки
`"number"` здесь нет, потому что `+` умеет и складывать, и склеивать.

## Ещё уровень вниз: ToPrimitive

[7.1.1 ToPrimitive](https://tc39.es/ecma262/#sec-toprimitive):

1. Если `input` — объект:
   1. `Let exoticToPrimitive be ? GetMethod(input, %Symbol.toPrimitive%).`
   2. Если метод есть — вызвать его с подсказкой (`"default"`, если `preferredType`
      не передан) и вернуть результат; если метод вернул объект — `TypeError`.
   3. Если `preferredType` не передан — считать его `number`.
   4. `Return ? OrdinaryToPrimitive(input, preferredType).`
2. Иначе вернуть `input` как есть.

Шаг 1.3 — тот самый, из-за которого `"default"` на практике почти совпадает с
`"number"`: подсказка `"default"` доезжает до пользовательского
`Symbol.toPrimitive`, но если его нет, дальше идёт `number`.

[7.1.1.1 OrdinaryToPrimitive](https://tc39.es/ecma262/#sec-ordinarytoprimitive):

1. Если подсказка `string` — порядок методов `« "toString", "valueOf" »`,
   иначе `« "valueOf", "toString" »`.
2. Для каждого имени: если метод вызываемый — вызвать; если результат не объект —
   вернуть его.
3. Ничего не подошло — `TypeError`.

Третий и четвёртый разделы вывода `plus-operator.mjs` проверяют обе ветки: какая
подсказка приходит от каждой операции и в каком порядке дёргаются `valueOf` и
`toString`, когда `Symbol.toPrimitive` не задан.

## Что из этого следует для компилятора

Выражение `a + b` — не инструкция сложения. В общем случае за ним стоит:
чтение двух ссылок, два потенциальных вызова геттеров, два `ToPrimitive`
(и до двух вызовов пользовательских методов внутри каждого), проверка на строку,
приведение к числу и только потом арифметика. Любой из этих вызовов может бросить
исключение, изменить любую переменную в программе или вернуть на второй раз другое
значение.

Отсюда растут два наблюдения, которые пригодятся в разделах 09–11:

- **Спекуляция неизбежна.** Единственный способ получить машинное сложение — угадать
  типы по наблюдениям и подстраховаться проверкой. Не угадали — деоптимизация.
- **Наблюдаемость определяет границы.** Компилятор вправе делать что угодно, пока
  результат неотличим. Но «неотличим» здесь измеряется числом вызовов геттера, а не
  только итоговым значением, — и это резко сужает набор законных преобразований.

## Как проверять себя

- **Node или d8** — быстрее всего. Ловушка: результат одной реализации не всегда
  равен требованию спецификации, особенно в свежих фичах.
- **[engine262](https://engine262.js.org/)** — реализация ECMA-262 на JavaScript,
  написанная почти дословно по алгоритмам. Полезна, когда непонятно, как шаг
  выглядит в коде.
- **[test262](https://github.com/tc39/test262)** — официальный набор тестов
  соответствия. Хороший способ узнать, какие именно граничные случаи считаются
  важными: по имени операции легко найти файлы с проверками.

## Мини-упражнения

1. Пройдите по шагам `[] == false` и объясните результат, не заглядывая в статьи.
   Понадобится [7.2.13 IsLooselyEqual](https://tc39.es/ecma262/#sec-islooselyequal).
2. Найдите в спецификации, почему `typeof` не бросает на необъявленном имени.
   Подсказка: искать надо в описании `typeof`, а не в разделе про ссылки.
3. Объясните, почему `console.log({} + [])` печатает `"[object Object]"`, а
   значение завершения `eval('{} + []')` равно `0`. Ответ лежит в грамматике, а не
   в приведении типов.
4. Найдите алгоритм, из которого следует поведение `let` в цикле `for`
   ([14.7.4.3 ForBodyEvaluation](https://tc39.es/ecma262/#sec-forbodyevaluation)),
   и сопоставьте его с соответствующим разделом `hoisting-and-tdz.mjs`.
