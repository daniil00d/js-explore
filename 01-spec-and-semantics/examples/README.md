# Примеры: спецификация и семантика

Зависимостей нет, всё запускается голым Node (проверено на Node 22.14 / V8 12.4).
Флаги не нужны: этот раздел про правила языка, а не про внутренности движка.

## Быстрый старт

```bash
node 01-spec-and-semantics/examples/hoisting-and-tdz.mjs
node 01-spec-and-semantics/examples/early-errors.mjs
node 01-spec-and-semantics/examples/asi-traps.mjs
node 01-spec-and-semantics/examples/strict-vs-sloppy.mjs
node 01-spec-and-semantics/examples/modules-vs-scripts.mjs
node 01-spec-and-semantics/examples/optimization-blockers.mjs
node 01-spec-and-semantics/examples/plus-operator.mjs
```

## В каком порядке читать

1. **`hoisting-and-tdz.mjs`** — самая базовая вещь: среда создаётся до выполнения
   кода, и все «странности» подъёма следуют из этого.
2. **`early-errors.mjs`** — граница между «программа не собралась» и «программа
   упала». Здесь же видно, что спецификация сама содержит статический анализ.
3. **`asi-traps.mjs`** — единственное место, где перенос строки влияет на смысл.
   Полезно один раз увидеть весь список исключений.
4. **`strict-vs-sloppy.mjs`** — два режима одного языка, включая случаи, когда
   один и тот же текст в одном режиме программа, а в другом синтаксическая ошибка.
5. **`modules-vs-scripts.mjs`** — почему граф ES-модулей статичен, а граф `require`
   нет. Прямой пролог к разделу про сборщики.
6. **`optimization-blockers.mjs`** — конструкции, из-за которых компилятор обязан
   отказаться от очевидных оптимизаций. Пригодится в разделах 03, 07 и 11.
7. **`plus-operator.mjs`** вместе с **`spec-walkthrough.md`** — как проверить
   спецификацию кодом: сначала читаем алгоритм, потом наблюдаем предсказанный
   порядок побочных эффектов.

## Как это устроено внутри

Многие правила проще показать на коде, который не должен запуститься. Поэтому
фрагменты выполняются через `node:vm`, а не пишутся прямо в файл: ранняя ошибка
уронила бы весь пример ещё до печати первой строки. Заодно `vm` даёт нестрогий
контекст — в модуле нельзя написать ни `with`, ни восьмеричный литерал.

`harness.mjs` различает два случая: `compile()` только компилирует фрагмент, не
выполняя его (так видно ровно ранние ошибки), а `run()` выполняет и возвращает
значение последнего выражения.

## Что стоит попробовать самому

- Добавьте в `early-errors.mjs` свои фрагменты и угадывайте вердикт до запуска.
  Хорошие кандидаты: `class C extends 1 {}`, `({ ...rest, a } = {})`,
  `async function f() { await await 1 }`.
- В `asi-traps.mjs` уберите ⏎ из ловушек и посмотрите, что меняется.
- В `optimization-blockers.mjs` замените геттер на обычное поле и убедитесь, что
  наблюдаемых обращений больше нет — это и есть тот случай, когда движку разрешено
  кешировать чтение.
- Скормите отдельные фрагменты другому движку (`v8`, `jsc`, `sm` из jsvu — установка
  описана в [../../00-setup/examples/d8-setup.md](../../00-setup/examples/d8-setup.md))
  и сравните сообщения об ошибках: поведение обязано совпасть, тексты — нет. Сами
  примеры там не запустятся, они опираются на `node:vm` и модули Node.
